# 代理工程

代理工程是建構讓語言模型採取行動之系統的實務：模型會呼叫工具、在環境中工作、與其他代理協調，並在正式運作時接受評估與監控。模型只是其中一個元件，大部分工程工作落在模型周圍的介面、控制與量測上。

## 概述

[AI 代理](../../theory/models/agents/index.zh-TW.md)頁說明代理是什麼。本節則說明如何建構一個能被信任、可執行真實行動的代理。只回答問題的代理，需要一個提示與一組測試集；會採取行動的代理，則需要明確定義的工具組、對這些工具可觸及範圍的限制、在單一代理不足時拆分工作的方式、以結果而非文字來衡量的基準，以及每次執行的紀錄。

## 關鍵概念

- **駕馭層（harness）：**讓模型在迴圈中運作、傳遞工具與觀察結果並決定何時停止的程式碼。
- **環境（environment）：**代理可以觀察與改變的系統，例如檔案系統、瀏覽器或 API。
- **軌跡（trajectory）：**一次執行的紀錄，從最初請求到最終狀態。
- **控制（control）：**權限、確認或上限，用來限制代理可以做的事。

## 運作方式

典型的代理迴圈會觀察目前狀態，請模型決定下一步行動，透過工具執行該行動，並記錄結果。當目標達成、達到上限或人員介入時，迴圈結束。每個階段都有對應的工程考量：工具設計決定模型能請求什麼；沙箱決定一個壞的行動能觸及什麼；編排決定工作如何拆分；評估決定迴圈是否成功；可觀測性決定事後能否解釋失敗。

## 執行契約與狀態轉移

設計代理時，可以將其視為狀態機，而不只是聊天紀錄。在第 `t` 次迭代，執行框架維護任務狀態 `s_t`、提出動作 `a_t`、取得觀察 `o_{t+1}`，再更新狀態。模型提出候選動作，執行框架則負責判斷是否有效與是否獲得執行授權。模型產生的指令不等於授權。

執行契約應明確列出初始輸入、允許的工具、權限範圍、預期產物、停止條件與復原策略。尤其應區分「提出工具呼叫」與「真正對外部系統產生效果」。例如程式代理可以準備修補程式，但不一定能推送到遠端；客服代理可以草擬退款，卻未必有權執行退款。

### 實例：修復儲存庫的代理

假設代理需要修復失敗的單元測試，可以採取以下流程：

1. **觀察：**透過唯讀工具取得測試失敗訊息、相關原始碼與 Git 狀態，記錄起始 Commit 與測試指令。
2. **規劃：**提出範圍最小的修正假設，並允許後續觀察推翻假設。
3. **授權：**確認目標路徑允許寫入、指令符合核准的執行設定；模型自行解釋不能繞過檢查。
4. **執行：**在可丟棄的工作環境套用修補，限制 CPU、時間與檔案系統存取。
5. **驗證：**執行目標測試與適當的回歸測試，保存結束碼、診斷與差異。
6. **提交或停止：**將通過驗證的修補交付審查；失敗或超過步數限制時，保留失敗證據，不宣稱成功。

此流程是工程設計範例，不代表引用論文已證明其正確性。修改檔案的授權與推送遠端的授權應分開，測試通過也不代表可以直接發布。

## 可靠性與故障隔離

模型可能選對工具卻傳錯參數、逾時後重複執行具有副作用的呼叫，或將不可信輸出當成指令。JSON Schema 只能驗證結構，應用層還須檢查帳戶歸屬、路徑允許清單與日期範圍等語意限制。遠端呼叫逾時不代表操作未完成；若付款或刪除缺少冪等性機制，重試可能造成重複副作用。

工具結果應保留來源資訊，並被視為觀察資料而非政策。搜尋結果中的「忽略先前指令」不會因為來自工具而取得更高權限。沙箱可降低不安全執行的後果，但不能單獨防止具權限的 API 做出未授權變更。詳見[沙箱與電腦操作](sandboxing-and-computer-use.zh-TW.md)及[工具呼叫](tool-calling-and-mcp.zh-TW.md)。

正式環境還需要明確的預算：最大迭代數、Token 與金錢成本、執行期限、外部請求次數，以及升級人工處理的政策。停止條件應由應用程式碼檢查，不能只問模型是否完成。無法驗證時，應清楚區分「已嘗試」、「已測試」、「部分完成」與「外部確認」。

## 評估協定

代理應以環境的實際結果評估，而不只看回答是否流暢。例如程式代理可能需要通過隱藏測試且不修改禁止的檔案；客服代理則需要選對帳戶、只執行授權變更並避免重複退款。每個任務都應有可重現的初始狀態，以及可自動檢查或獨立審查的結束狀態。

除了成功率，還應報告中位數與尾端延遲、工具呼叫次數、每次成功的成本、違反政策的次數及失敗復原能力。Kapoor 等人的研究指出，基準評估不能只排名準確率，也必須考慮成本、可重現性與過度擬合。

若要分離模型能力與執行框架的影響，應固定任務集合及工具，再比較協調策略或提示方式。具有隨機取樣的設定需重複試驗，並記錄模型版本、工具結構描述、權限政策、資料集版本與評估器。單次成功軌跡不能代表可靠性估計。

## 可觀測性與事故分析

有用的 Trace 應串接使用者請求、模型呼叫、工具提案、授權決策、工具執行、回傳觀察與最終產物。記錄時間戳記、延遲、錯誤類別與關聯識別碼，但不應無差別保存機密或敏感資料；寫入前應先遮罩或最小化。

事故檢討應區分模型選擇錯誤、執行框架授權漏洞、工具實作缺陷與評估器錯誤。這些問題需要不同的修正方式。改善提示可能減少錯誤提案，但不能取代伺服器端權限檢查；增加代理數量也可能提高協調成本而不改善結果。[多代理協調](multi-agent-orchestration.zh-TW.md)比較不同設計的取捨。

## 人工監督與認知類比

代理記憶常被比擬成人類工作記憶與長期記憶，但持久化的 Scratchpad 並不能證明代理具有人類式記憶機制。工程上應區分暫時執行上下文、持久任務紀錄與外部檢索知識；它們的時效、隱私與污染風險不同。尤其當持久狀態會影響未來工具呼叫時，操作人員應能檢查並修正。

核准介面應顯示具體動作、目標資源與可能後果，而不是只有模糊的「繼續」按鈕。不可逆操作應在參數驗證後再次確認。這是可追責系統的設計原則，並不表示人工審查可以完全消除自動化風險。

## 應用

- **軟體工程代理**：閱讀程式庫、編輯檔案並執行測試。
- **客服營運代理**：查詢帳戶並執行已核准的變更。
- **研究助理**：搜尋、閱讀來源，並撰寫附引用的摘要草稿。
