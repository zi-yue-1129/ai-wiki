# CaMeL：以設計防禦提示注入

CaMeL（Debenedetti et al., 2025）是一種供 LLM 代理人使用的防禦方法，它不依賴模型忽略注入的指令。它在模型外圍放置一層一般軟體，從受信任的使用者請求中取得任務的控制流與資料流，並依安全政策檢查每一次工具呼叫。它是 [沙箱與電腦操作代理人](../index.md)頁面中三個里程碑方法之一，也是該頁中最清楚體現「隔離副作用的權限模型」的例子。

## 概述

提示注入發生在代理人讀取到不受信任的內容（例如網頁或工具結果）時，而這些內容含有它隨後會遵循的指令。既有的防禦大多作用於模型本身，例如分隔符號、提醒或訓練。這些做法可以減少攻擊，但無法提供保證，而且新的攻擊經常能夠突破它們。

CaMeL 改變了問題的提法。它不再詢問模型能否抵抗注入的文字，而是詢問注入的文字能否觸及系統中重要的部分。代理人的行為有兩個部分。**控制流**是代理人將採取的步驟順序；**資料流**則是每個值從何而來、要往何處去。注入可能破壞其中任何一者。CaMeL 從受信任的請求中固定控制流，使不受信任的資料無法決定執行哪個工具；同時追蹤資料流，使政策能阻止某些值流入不該到達的工具。

## 關鍵概念

- **特權 LLM（P-LLM）**：只看見使用者查詢，並以 Python 程式碼撰寫計畫的模型。它從不看見工具輸出的內容。
- **隔離 LLM（Q-LLM）**：把不受信任的文字解析為結構化形式的模型。它沒有工具存取權，因此即使注入的內容傳到它那裡，也無法直接採取行動。
- **能力（capability）**：附加在每個值上的標籤，記錄該值的來源以及誰可以讀取它。
- **安全政策（security policy）**：根據輸入的能力，決定某次工具呼叫是否允許的函式。
- **直譯器（interpreter）**：自訂的 Python 直譯器，負責執行計畫、記錄資料流圖，並在執行每個工具前檢查政策。

## 運作方式

論文沿用雙 LLM 模式（Dual-LLM pattern），即由特權模型規劃、隔離模型閱讀，並加上一個直譯器來執行這種分離。其迴圈如下：

1. P-LLM 接收使用者查詢與可用工具（包括作為可呼叫函式的 Q-LLM），並撰寫表達計畫的 Python 程式碼。
2. 直譯器執行程式碼。每個工具的輸出都存入變數，且工具會附加描述其來源與讀者的能力。
3. 當計畫需要從不受信任的文字中擷取資訊時，它會呼叫 Q-LLM，並指定預期的輸出結構。Q-LLM 只回傳結構化的值。
4. 在呼叫工具之前，直譯器利用資料流圖收集該呼叫所依賴變數的能力，並套用政策。允許時執行，不允許時阻擋。
5. 若 Q-LLM 回報資訊不足，直譯器會拋出錯誤，並要求 P-LLM 產生不同的程式碼。

P-LLM 從不看見工具輸出，因此注入的指令可以改變值，但無法改變計畫的步驟；而這些值在到達會改變狀態的工具之前，都會經過政策檢查。

## 結果

- **AgentDojo。** 摘要報告，CaMeL 以可證明的安全性解決了 77% 的任務，未加防禦的系統則為 84%。兩者的差距即是此防禦在任務成功率上的代價。
- **不使用政策時。** 即使沒有任何安全政策，CaMeL 也能降低所測試的每一個模型的成功攻擊數，其中一個模型由 300 次降為 0 次。銀行與旅遊兩個測試組中，仍有兩項注入任務在某些執行中成功。
- **效用。** 在大多數測試組中，效用與原生工具呼叫相近；旅遊測試組的下降較大。

## 限制

- **非目標。** CaMeL 無法防禦那些不改變控制流與資料流的攻擊，例如錯誤轉述一封電子郵件的摘要。論文建議，在介面中顯示值的來源，有助於使用者察覺此類情況。
- **人工參與。** 系統並非完全自主。當查詢含糊時，使用者可能需要澄清預期的流程。
- **政策的工作量。** 政策必須撰寫，但可以相當細緻，如論文中的行事曆範例所示。

## 開放問題

- **誰來撰寫政策。** 政策可能來自平台、應用程式或使用者，合適的分工尚無定論。
- **圖形介面。** CaMeL 假設工具輸出是結構化的。它的概念能否移植到以螢幕截圖為基礎的代理人，這在[沙箱主題頁](../index.md)中討論，目前仍是開放問題。
- **殘餘攻擊。** 殘留的成功攻擊顯示，即使是以設計為基礎的防禦也仍有缺口。

## 參考文獻

### 奠基性論文

- Debenedetti, E. et al. (2025). *Defeating Prompt Injections by Design*. arXiv. https://arxiv.org/abs/2503.18813 — 提出 CaMeL，分離控制流與資料流，並在呼叫工具時執行以能力為基礎的安全政策。
- Debenedetti, E. et al. (2024). *AgentDojo: A Dynamic Environment to Evaluate Prompt Injection Attacks and Defenses for LLM Agents*. arXiv. https://arxiv.org/abs/2406.13352 — 包含 97 個工具使用任務與 629 個安全測試案例的基準環境，用於評估 CaMeL。
- Greshake, K. et al. (2023). *Not what you've signed up for: Compromising Real-World LLM-Integrated Applications with Indirect Prompt Injection*. arXiv. https://arxiv.org/abs/2302.12173 — 顯示檢索資料中的指令可以劫持整合 LLM 的應用程式，這正是 CaMeL 所針對的威脅。
- Lampson, B. W. (1973). *A note on the confinement problem*. Communications of the ACM. https://doi.org/10.1145/362375.362389 — 定義遏制問題，即如何阻止程式洩漏資訊的較早問題，資訊流控制正是針對此問題。
- Saltzer, J. H. & Schroeder, M. D. (1975). *The protection of information in computer systems*. Proceedings of the IEEE. https://doi.org/10.1109/PROC.1975.9939 — 保護原則的經典陳述，包括最小權限，後續的存取控制設計皆以此為基礎。
